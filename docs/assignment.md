# Лабораторная работа «Ничего не падает»

Вы разрабатываете консольное приложение для работы с расписанием. Оно должно хранить корректные занятия, выбирать их по дате или типу и сообщать об ошибках во входных данных.

Главная задача — спроектировать модель так, чтобы её нельзя было испортить через публичный API. Проверка только при чтении файла недостаточна: модель должна защищать себя и при прямом вызове конструктора.

**Работа сдаётся один раз целиком.** Два этапа ниже — логические части реализации. Общий срок указан в карточке задания в Academy.

Команды, типы занятий в файлах, сообщения и примеры вывода используют английский язык. В учебных входных файлах темы, места и имена преподавателей также записываются латиницей. Для отсутствующего значения используется обычный символ `-`.

В шаблоне уже готовы:

## Этап 1. Модель, которую нельзя сломать

Создайте интерфейс `Session` с общими свойствами:

```kotlin
interface Session {
    val date: LocalDate
    val topic: String
}
```

Используйте `LocalDate` из пакета `java.time`.

Реализуйте четыре конечных типа:

| Тип занятия | Свойства и ограничения |
|---|---|
| Лекция | Дата, тема, место, хотя бы один преподаватель |
| Практикум | Дата, тема, место, хотя бы один преподаватель |
| Сдача | Дата, тема, место, не менее двух разных преподавателей |
| Отмена | Только дата и тема |

У отмены **не должно быть свойств места и преподавателей**, даже nullable-свойств.

Для всех занятий действуют правила:

- год находится в диапазоне `1..9999`;
- тема непустая и не состоит только из пробельных символов;
- внешние пробельные символы и управляющие символы запрещены;
- внутренние пробелы в теме, месте и имени разрешены;
- у действующего занятия место непустое и не равно `-`;
- список преподавателей не содержит пустых имён, имени `-` и повторов;
- регистр значим: `Ivanov` и `ivanov` считаются разными именами;
- порядок преподавателей сохраняется.

Ничего автоматически не исправляйте: не обрезайте пробелы, не меняйте регистр и не удаляйте дубликаты.

Обязательные ограничения должны проверяться при создании объекта. Нарушение контракта модели из программного кода должно приводить к понятному `IllegalArgumentException`.

Выберите между обычным `class` и `data class` самостоятельно. В README объясните выбор. Если используете `data class`, его `copy()` обязан сохранять все инварианты.

### Защита коллекций

После создания занятия изменение переданного списка не должно менять объект:

```kotlin
val names = mutableListOf("Ivanov", "Petrov")

// Создайте сдачу с преподавателями из names.

names.clear()

// У созданной сдачи по-прежнему должны остаться два преподавателя.
```

Получение списка преподавателей через публичное свойство тоже не должно позволять изменить состояние занятия.

Проверьте обе ситуации отдельно: изменение исходного списка и попытку изменить список, полученный из объекта.

### Реестр расписания

Реализуйте хранение занятий в памяти через интерфейс:

```kotlin
interface SessionRepository {
    fun add(session: Session)
    fun addAll(sessions: List<Session>)
    fun all(): List<Session>
}
```

Контракт реестра:

- `add` добавляет одно занятие;
- `addAll` добавляет все переданные занятия в их исходном порядке;
- одинаковые занятия допускаются и сохраняются отдельно;
- `all` возвращает снимок текущего содержимого;
- изменение реестра после вызова `all` не меняет ранее полученный снимок;
- через снимок нельзя изменить внутреннее состояние реестра.

### Журналирование через делегирование

Создайте `AuditedSessionRepository`, который реализует интерфейс через `SessionRepository by delegate`.

Здесь `delegate` — имя объекта внутреннего реестра, которому обёртка передаёт выполнение операций.

Обёртка должна:

- передавать хранение внутреннему реестру;
- вести журнал успешно завершённых операций добавления;
- считать общее количество добавленных занятий.

Событие журнала содержит название операции и количество добавленных занятий. Журнал хранится в памяти.

Правила:

- успешный `add` создаёт одно событие с количеством `1`;
- успешный `addAll` создаёт одно событие с размером переданного списка;
- `addAll(emptyList())` создаёт событие с количеством `0`;
- `all` не создаёт событий;
- внутренние вызовы делегата не должны приводить к повторному журналированию.

Например, после добавления одного занятия и пакета из трёх занятий:

```text
Sessions: 4
Added: 4
Audit events: 2
```

В README ответьте: **почему переопределить только `add` недостаточно для учёта вызовов `addAll`?**

Журнал не печатается автоматически в консоль. Команды второго этапа должны сохранять установленный формат вывода.

Также проверьте корректное создание всех четырёх типов, снимки реестра и журналирование одиночного и пакетного добавления.

## Этап 2. Разбор файла и ошибки как данные

Его стоит выполнять после занятия «Ошибки как данные» — сделайте `Session` sealed-интерфейсом.

Входной файл содержит строки из пяти полей:

```text
date|type|topic|location|teachers
```

Пример:

```text
2026-10-05|LECTURE|Classes and delegation|Room 312|Portnov
2026-10-08|PRACTICE|Domain modeling|Room 312|Anokhin
2026-10-15|EXAM|Oral exam 1|Room 401|Portnov,Stepanova
2026-10-19|CANCELLED|Lecture postponed|-|-
```

Завершающий перевод строки не создаёт дополнительную пустую строку.

Разрешённые значения типа: `LECTURE` — лекция, `PRACTICE` — практикум, `EXAM` — сдача, `CANCELLED` — отмена. Регистр значим.

Правила формата:

- разделитель полей — `|`;
- полей ровно пять, включая конечные пустые поля;
- преподаватели разделяются запятыми;
- дата имеет вид `YYYY-MM-DD`, год — четыре цифры от `0001` до `9999`;
- дата должна существовать;
- у отмены место и преподаватели записываются как `-`;
- пустая строка ошибочна;
- в пустом файле строк нет.

Результат разбора одной строки представьте своей sealed-иерархией: успешный результат с занятием или отказ со структурированной причиной и номером строки, начиная с единицы.

Не храните готовое сообщение или `Throwable` вместо причины. Преобразование причины в английское сообщение выполняет отдельная функция.

Некорректная входная строка должна давать результат отказа. Обработка следующих строк продолжается.

### Порядок проверок

На одну строку возвращается одна ошибка. Используйте следующий приоритет:

1. Нет `|` — неверный разделитель.
2. Полей не пять — неверное количество полей.
3. Есть пустое или полностью пробельное поле — первое такое поле в порядке следования.
4. Неверный формат или значение даты.
5. Неизвестный тип занятия.
6. У сдачи менее двух непустых и непробельных элементов списка, отличных от `-`.
7. Остальные нарушения домена.

Внутри пункта 7 проверяйте последовательно:

1. Управляющие символы.
2. Внешние пробельные символы.
3. Неверные поля отмены.
4. Недопустимое место действующего занятия.
5. Недопустимые элементы списка преподавателей.
6. Повторные имена преподавателей.

Если нарушение встречается в нескольких полях, выбирайте первое поле в порядке следования. В списке преподавателей выбирайте первый недопустимый элемент.

Обязательные сообщения:

```text
line N: invalid date "2026-13-45"
line N: empty required field "date"
line N: invalid field separator
line N: unknown session type "SEMINAR"
line N: type "EXAM" requires at least 2 teachers, got 1
line N: got 6 fields, expected 5
```

Имена полей: `date`, `type`, `topic`, `location`, `teachers`. Кавычки — обычные двойные `"`. Параметры сообщений подставляются из входной строки.

В значениях внутри сообщений экранируйте обратную косую черту как `\\`, двойную кавычку как `\"`, а управляющие и не-ASCII символы — как `\uXXXX` (четыре шестнадцатеричные цифры на каждый UTF-16 символ). Так даже повреждённый вход не добавит перевод строки или русский текст в сообщение. Это относится к форматтеру ошибок; сами значения модели автоматически не изменяйте.

Для остальных причин придумайте отдельные понятные сообщения и зафиксируйте их в README.

Добавьте тесты на несколько дефектов одновременно. Например:

```text
2026-13-45|SEMINAR|Topic|Room 1|Ivanov
```

Здесь должна быть ошибка даты.

```text
2026-10-05|EXAM|Topic|Room 1|Ivanov,Ivanov
```

Здесь должна быть ошибка повторного имени.

### Команды приложения

Реализуйте поведение трёх команд:

```text
schedule period --file PATH --from YYYY-MM-DD --to YYYY-MM-DD
schedule type --file PATH --type LECTURE
schedule errors --file PATH
```

Здесь `schedule` — условное имя вашего приложения, а не встроенная команда терминала. Выполняйте команды из корня проекта: папки, в которой находятся `gradlew.bat`, `settings.gradle.kts` и каталог `samples`. Можно использовать вкладку **Terminal** в IntelliJ IDEA или отдельный терминал.

**Windows PowerShell.** Сначала соберите приложение и создайте файлы запуска:

```powershell
.\gradlew.bat build :app:installDist
```

После успешной сборки Gradle создаст скрипт `app/build/install/schedule/bin/schedule.bat`. Запустите его по пути:

```powershell
.\app\build\install\schedule\bin\schedule.bat period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
.\app\build\install\schedule\bin\schedule.bat type --file samples/dirty.txt --type EXAM
.\app\build\install\schedule\bin\schedule.bat errors --file samples/dirty.txt
```

**Linux/macOS.**

```bash
bash ./gradlew build :app:installDist
./app/build/install/schedule/bin/schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
./app/build/install/schedule/bin/schedule type --file samples/dirty.txt --type EXAM
./app/build/install/schedule/bin/schedule errors --file samples/dirty.txt
```

Для запуска во время разработки также можно использовать Gradle напрямую, без создания скрипта приложения:

```powershell
.\gradlew.bat :app:run --args="period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13"
```

Аргументы приложения получает готовая функция `fun main(args: Array<String>)`. Например, для команды `period` массив начинается с `"period"`, `"--file"`, `"samples/clean.txt"`. Готовый код разбирает массив и вызывает соответствующую функцию из `Commands.kt`:

| Функция, которую вы дописываете | Данные готовой команды |
|---|---|
| `runPeriod(command: Command.Period)` | `command.file`, `command.from`, `command.to` |
| `runType(command: Command.ByType)` | `command.file`, `command.type` |
| `runErrors(command: Command.Errors)` | `command.file` |

Функции печатают результат и возвращают код завершения. Повторно разбирать аргументы или писать диспетчер команд не нужно. `SessionType` в шаблоне описывает метки для CLI; он не заменяет четыре класса вашей модели.

Используйте готовое чтение строк внутри обработчика:

```kotlin
forEachScheduleLine(command.file) { number, line ->
    // Передайте number и line в свой парсер и обработайте результат.
}
```

Итог печатайте после завершения чтения. Если возникнет ошибка чтения, она дойдёт до готовой точки входа, которая напечатает `Cannot read file` и вернёт `2`. Не перехватывайте в обработчике все исключения и не превращайте ошибки программирования в отказ входной строки.

Путь `samples/clean.txt` отсчитывается от текущей рабочей папки, поэтому запуск из корня проекта обязателен для приведённых примеров.

Порядок пар параметр/значение произволен. Каждый предусмотренный для команды параметр обязателен и встречается ровно один раз.

Неизвестная команда, лишние или повторные параметры, отсутствие значения, недопустимая дата или тип и `from > to` считаются ошибками аргументов. Синтаксис `--key=value` не поддерживается.

Для имени файла, начинающегося с `--`, используйте путь `./--name`.

Команда `period` печатает занятия в диапазоне дат включительно:

```text
2026-10-05 | LECTURE | Classes and delegation | Room 312
Total: 1
```

Команда `type` выбирает один из четырёх типов и дополнительно печатает преподавателей:

```text
2026-10-15 | EXAM | Oral exam 1 | Room 401 | Portnov, Stepanova
Total: 1
```

Имена преподавателей разделяются запятой с пробелом. У отмены вместо места и преподавателей выводится `-`.

Команда `errors` печатает ошибки в порядке строк файла и итог:

```text
Rejected: K of M
```

`M` — количество строк файла, `K` — количество отклонённых строк.

Для всех команд:

- сохраняйте порядок файла;
- проверяйте весь файл, даже если занятие не попадает в фильтр;
- пропускайте ошибочные строки в `period` и `type`;
- печатайте итог даже при нулевом результате;
- используйте разделитель ` | `;
- не добавляйте заголовков таблицы и сообщений журнала.

Результаты и сообщения об ошибках выводите через `println`.

Коды завершения:

| Код | Значение |
|---|---|
| `0` | Файл обработан полностью, отклонённых строк нет |
| `1` | Файл обработан полностью, есть отклонённые строки |
| `2` | Неверные аргументы или ошибка чтения файла |

Ошибочные строки учитываются в коде завершения `period` и `type`, даже если они не попадают в фильтр.

Готовый запуск выводит `Invalid arguments` при неверных аргументах и `Cannot read file` при ошибке чтения, без стектрейса. Если ошибка чтения возникла после обработки части файла, ранее напечатанные строки сохраняются; итог успешного завершения не печатается.

### Проверка результата

Для обязательной сдачи используйте:

- `clean.txt` — 200 корректных строк;
- `dirty.txt` — 500 строк, из которых 164 отклоняются;
- `empty.txt` — пустой файл;
- собственные небольшие файлы с пограничными случаями.

Сравните вывод с соответствующими `*.expected`. Помните: `clean.expected` относится к команде:

```text
schedule period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13
```

После реализации и сборки запустите `python tools/verify.py` (на Linux/macOS — `python3`). Проверка сравнивает английский вывод и коды завершения на небольших файлах. Дополнительно она проверяет диапазон за октябрь и каждый из четырёх типов на коротком файле.

Обычная сборка и базовая проверка GitHub Actions проходят уже в шаблоне: они проверяют готовый код и ваши тесты. Это ещё не означает, что лабораторная выполнена. Проверка `tools/verify.py` должна пройти на вашем решении; заглушки её не проходят.

**Автоматические проверки предназначены для самопроверки.** В репозитории уже есть тесты готового запуска и сравнение вывода с эталонами на заданных примерах. Их успешное прохождение помогает понять, что основные проверяемые сценарии, скорее всего, реализованы верно. Но это ограниченный набор тестов: он не доказывает правильность решения во всех случаях и не означает автоматическую сдачу работы.

**Основную проверку и итоговую оценку проводит лабник.** Он изучает код, проверяет устройство модели, соблюдение инвариантов, защиту коллекций, делегирование, обработку ошибок и пограничные случаи. Собственные тесты и объяснение принятых решений остаются обязательной частью работы.

## Задание со звёздочкой: перенос занятия

Добавьте операцию переноса действующего занятия на другую дату.

Она должна:

- возвращать новое занятие того же типа;
- сохранять тему, место и преподавателей;
- оставлять исходное занятие без изменений;
- проверять допустимость новой даты;
- возвращать типизированный отказ при попытке перенести отменённое занятие.

Не добавляйте новую команду CLI: достаточно метода или функции и тестов.

## Что сдавать

Отправьте ссылку на свой репозиторий.

В нём должны быть:

- реализация;
- проходящие тесты;
- инструкции сборки и запуска;
- объяснение выбора типов;
- ответы о защите коллекций и поведении делегирования;
- примеры собственных проверок, которыми вы пытались сломать модель.
