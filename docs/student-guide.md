# Памятка по реализации

## Как команда попадает в ваш код

Готовая `main(args)` вызывает `parseCommand`. Парсер превращает строки аргументов в `Command.Period`, `Command.ByType` или `Command.Errors`. Затем запуск вызывает `runPeriod`, `runType` или `runErrors` из `Commands.kt`.

Например, `period --file samples/clean.txt --from 2026-09-28 --to 2027-05-13` передаёт в `runPeriod` объект с полями `file`, `from` и `to`. Даты уже представлены как `LocalDate` и проверены; `from <= to`. Для `type` значение `command.type` уже проверено и представлено через `SessionType`.

Вам нужно реализовать действия обработчиков, а не разбирать эти аргументы повторно. Содержимое строки расписания разбирает ваш отдельный парсер: готовый CLI его не реализует.

## Чтение файла

В обработчике используйте готовую функцию:

```kotlin
forEachScheduleLine(command.file) { number, line ->
    // number — номер строки, начиная с 1, тип Long.
    // line — текст строки без перевода строки.
    // Вызовите свой парсер и обработайте его результат.
}
```

Функция читает по одной строке, поддерживает LF и CRLF, закрывает файл. Пустой файл не вызывает блок ни разу; завершающий перевод строки не создаёт лишнюю строку.

Печатайте итог только после завершения чтения. Ошибки чтения обрабатывает готовая точка входа: сообщение `Cannot read file`, код `2`. Если чтение оборвалось, уже напечатанные строки остаются, итог не печатается. Не ловите `Exception` или `Throwable` вокруг всей обработки: иначе ошибка вашего кода может превратиться в обычную ошибку входных данных.

Ожидаемый дефект строки представьте своим вариантом отказа со структурированной причиной. Проверки конструктора должны оставаться обязательными и при создании модели без файла.

## Вывод и завершение

Используйте `println`:

```kotlin
println("2026-10-05 | LECTURE | Classes and delegation | Room 312")
println("Total: 1")
```

Обработчик возвращает `0`, если весь файл корректен, или `1`, если хотя бы одна строка отклонена. Это относится ко всем командам, даже когда отказ не попадает в фильтр. Вызывать `exitProcess` в обработчиках не нужно: его вызывает `main`.

Сообщения журнала реестра не печатайте вместе с результатами команд.

## Неизменяемые коллекции

`val teachers: List<String>` не гарантирует неизменяемость: у вызывающего кода может остаться ссылка на исходный `MutableList`. `toList()` отделяет список от исходного, но выданную копию тоже нужно защищать от изменения. В JVM-проекте для этого подходит `java.util.List.copyOf`. Проверяйте инварианты по сохранённой копии.

Конструктор и `copy()` у `data class` должны сохранять одни и те же инварианты. Помните, что автоматически созданный `copy` работает со свойствами первичного конструктора: продумайте, какую коллекцию хранит объект и выдаёт его API. У отмены не объявляйте свойства места и преподавателей.

Снимок реестра должен быть отделён от его внутренней коллекции. Защита коллекции реестра и защита самих объектов занятий — отдельные задачи.

## Тесты

Тесты готового запуска находятся в `CliTest.kt`. Добавляйте собственные тесты в `app/src/test/kotlin`; готовые тесты сохраняйте.

Метод теста помечается `@Test`. `assertIs` проверяет вариант результата, `assertEquals` — его данные, `assertFailsWith<IllegalArgumentException>` — нарушение контракта конструктора.

Начните с прямого создания модели без парсера: пустая тема, неверный год, недостаточное количество преподавателей, дубликаты. Отдельно проверьте изменение исходного и выданного списков.

Для парсера задавайте короткие строки и ожидаемую причину явно. Проверьте конечные пустые поля, LF/CRLF, пустой файл, несколько дефектов одновременно и порядок проверок из условия. Не вычисляйте ожидаемое сообщение той же функцией, которую проверяете.

Для команд проверьте включительность дат, порядок файла, нулевой результат и отказ вне выбранного диапазона. Для реестра — снимок и журналирование одиночного и пакетного добавления без двойного учёта.

Команда тестов: `.\gradlew.bat test` на Windows или `bash ./gradlew test` на Linux/macOS. Проверка полного вывода: `python tools/verify.py` после `installDist`.
